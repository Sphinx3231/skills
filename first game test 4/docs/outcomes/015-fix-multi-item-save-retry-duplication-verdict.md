## Code quality

Read the diff directly (not from the outcome doc's paraphrase). The fix:
- Introduces a plain local `const savedKeys: string[] = []` (not React
  state) scoped to one `confirmSaveItems()` call, pushed to synchronously
  after each successful `api.createLog` resolves inside the loop.
- On catch, prunes `items` via `setItems((prev) => prev.filter(...))`
  against `savedKeys` before returning to `'review-items'`.
- Appends an "(N item(s) already saved...)" suffix to the error message
  only when `savedKeys.length > 0`, preserving the original exact-text
  assertion for the first-item-fails case.

This is a correct, minimal, idiomatic fix for the stated bug. Using a plain
local array instead of new `ReviewItem` status fields matches the ticket's
first candidate approach and its own stated preference for the "lighter"
option since full atomicity is an explicit non-goal.

**Key-stability check (independently traced, not inherited):** `item.key`
is assigned once, at `pickAndAnalyze()` time (`log.tsx:123`,
`key: \`item-${index}\`),` derived from the scan-result array index at
creation and never regenerated by `updateItem`/`removeItem`. `savedKeys`
comparisons against `item.key` inside the same `confirmSaveItems()` call are
therefore safe — no risk of an unrelated item accidentally matching a saved
key within one scan's lifetime.

**UI-reachability claim, independently verified:** grepped every `setStep`
call in `log.tsx`. From `'review-items'`, the only two exits are (a)
`reset` (the "Discard" button, which fully clears `items`/`result`/
`photoUri` back to `'idle'`) and (b) `confirmSaveItems()` itself (success
path calls `finishLogging()`, which also resets). The `'idle'`-only
"Snap & Track" trigger (`pickAndAnalyze`) is not reachable from
`'review-items'` in the current UI — there is no "scan another item"
affordance on that screen. Tech-lead's claim holds today, confirmed by
independent trace of the render tree and step-transition graph, not by
re-reading the same claim.

**Is this a fragile invariant worth flagging in code?** Yes, mildly. The
correctness of `savedKeys.includes(item.key)`-based pruning implicitly
depends on `items` only ever being generated once per scan session (via
`analysis.items.map((item, index) => ({ ..., key: \`item-${index}\` }))`).
If a future ticket added an "add another item to this scan" or "rescan one
item" shortcut *from the `'review-items'` screen without a full reset*, and
that shortcut appended newly-scanned items using the same
`item-${index}`-from-zero scheme, it could silently collide with a
surviving pruned item's key and cause a stale-pruning or mis-attribution
bug — exactly the class of invariant that looks obviously safe today and
quietly breaks under later, unrelated feature work. This is worth a
one-line comment at the `key: \`item-${index}\`` assignment (log.tsx:123)
noting that key uniqueness assumes `items` is only ever (re)populated once
per scan, cleared entirely by `reset()`, and never appended to in place.
**This is a non-blocking architectural note, not a blocking issue** — no
such feature exists today, the ticket's scope doesn't touch that codepath,
and demanding a defensive comment for a scenario with zero current callers
would be scope creep on this ticket. Recommend the tech lead or whoever
picks up a future "review-items" enhancement add this comment then, or now
if trivial — non-blocking either way.

## Risk assessment

- **Reversibility**: fully reversible, no migrations, no schema changes, no
  irreversible data operations. Frontend-only.
- **Blast radius**: confined to the multi-item photo-scan retry path added
  in ticket 014; the single-item voice/barcode `confirmSave()` path is
  untouched (confirmed by diff — no lines outside `confirmSaveItems()`
  changed).
- **Residual known limitation** (explicitly out of scope, correctly
  deferred): no transactional atomicity across the save loop — a failure
  still leaves already-succeeded items as real rows with no server-side
  rollback. This ticket only closes the *retry-duplication* half of that
  limitation, which is exactly what it was scoped to do. Acceptable to
  defer; a future batch-endpoint ticket remains the right vehicle for full
  atomicity, as both the ticket and outcome doc already state.

## Verdict

Architecturally sound, in-scope, regression-free by both independent
re-run and independent mutation testing, and the outcome doc is accurate.
No blocking issues. One non-blocking architectural note recommended (a
one-line comment on the `item-${index}` key-generation invariant, for
whoever eventually adds a "review-items" screen enhancement) and one
janitorial item (`backend/nul`) flagged for the human, not this diff.
