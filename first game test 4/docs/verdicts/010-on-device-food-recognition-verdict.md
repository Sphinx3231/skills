## Decision

**MERGE.**

The shipped code matches the twice-approved plan, and the one property that mattered most across

exists, and the endpoint is authenticated and not hosted anywhere — but it becomes a **hard
deploy-time gate**, and it is the highest-priority follow-up out of this ticket.

### The two corrections to the plan's own sketches

Both were explicitly invited by the plan ("don't assume version parity"), and both are real bugs
caught by reading `@huggingface/transformers@4.2.0`'s source rather than assuming:

1. **`HF_HOME` does not exist in this library.** Cache relocation is the programmatic `env.cacheDir`
   property. Handled by importing the `env` singleton and setting it inside `defaultPipeline`
   before the first `pipeline()` call. I confirmed this works — not by reading, but by running the
   real model and printing the resolved directory (§5).
2. **The zero-shot pipeline substitutes candidate labels into a `hypothesis_template`** (default
   `'This is a photo of {}'`). Since every `prompt` is already a complete sentence, the default
   would have produced `"This is a photo of a photo of pizza"` — silently degrading *every*
   classification with no error. Fixed with `hypothesis_template: '{}'`. This is the single
   highest-value catch of the build, and `local-food-recognition.test.js:71` pins it
   (`assert.deepStrictEqual(results[0]._sawOptions, { hypothesis_template: "{}" })`).

**Drift found: none.** No new `Step`, no review-UI redesign, no calorie guard (correctly declined
per plan Step 0 item 3), no `analyze-text` changes, no scope creep into 008/009 territory.

## 2. Code quality

**Verdict: high. The `foodName` invariant is airtight by construction, not by convention.**

### The `foodName`-only-from-the-nutrition-table invariant

This was the single most safety-critical property across all four review rounds. It holds, and it
holds for a structural reason rather than a defensive one.

In `local-food-analysis.js` there are exactly **four** return sites, and I traced each:

| Return site | `foodName` source |
|---|---|
| `!top` (empty classifier output) | `NO_FOOD_RESULT` — frozen constant, `foodName: ""` |
| `anchorPrompts.has(top.label)` | `NO_FOOD_RESULT` — same frozen constant |
| `!nutrition` (defensive) | `NO_NUTRITION_RESULT` — frozen constant, `foodName: ""` |
| success | `nutrition.foodName` |

`nutrition` comes only from `lookupNutritionByLabel(matched.key)`, which is a single
`SELECT * FROM food_nutrition_reference WHERE label = ?` returning `row.food_name`. `matched.key` is
used **only** as that lookup key — it is never assigned to any output field. `top.label` (the raw
model prompt) is used **only** as a `Map`/`Set` lookup key. Neither ever reaches an output field.

Three properties make this genuinely airtight rather than merely currently-correct:

1. **The empty-string results are `Object.freeze`d module constants**, spread into fresh objects at
   return. A future edit cannot accidentally mutate the shared "couldn't identify" result.
2. **The lookup is by primary key into checked-in, version-controlled data.** The only way a raw
   prompt string could become a `foodName` is if someone hand-wrote a prompt string into
   `food-nutrition-data.js`'s `foodName` column. I checked: zero of the 36 `foodName` values equal
   any of the 39 prompts, zero contain the substring "a photo of", zero are blank/whitespace.
3. **There is no second writer to the table.** `food_nutrition_reference` is written in exactly one
   place — the `INSERT OR IGNORE` seed loop in `db/index.js` — sourced from that one checked-in
   file. No route, no user input, no migration writes to it.

Mutation probes M2 and M3 (below) confirm the test suite would catch a regression here, but the
stronger statement is that the design leaves no room for one.

**Also verified: the underscore-replace hack from the dropped Food-101 design is genuinely gone.**
No `.replace(/_/g, ' ')` anywhere in the new modules — `grep` confirms. Display names come from the
data file's `food_name` column ("Grilled chicken breast", "Sushi roll"), which is why they read
naturally rather than as de-underscored keys.

### The anchor-top-K confidence logic

Sound, and correctly ordered. Reading `local-food-analysis.js:61-86`:

- `anchorNearTop` is computed over `results.slice(0, 3)` **before** the anchor-in-top-1 early
  return, so it is available on every path that needs it.
- Anchor in top-1 → `NO_FOOD_RESULT`. Correct: if the model's best guess is "not food," there is no
  food name to prefill.
- Anchor at position 2 or 3 with a real food at top-1 → the food suggestion is still returned (so
  the user has something to edit rather than a dead end) but `confidence` is **forced** to `'low'`
  and the caveat is swapped to the "may not show a clearly recognizable food" wording. This is
  precisely the tech-lead's flagged dog-photo case, and the regression test hard-codes the spike's
  real numbers (0.564 waffles / 0.394 anchor, margin 0.170 — which top-1-only logic would have
  called "medium" with no warning at all).
- The `confidence = anchorNearTop ? "low" : baseConfidence` override is applied **after** the margin
  bands, so it can only ever downgrade, never upgrade. Correct direction.
- Margin bands (`>= 0.4` high, `>= 0.15` medium, else low) are honestly commented as *a deliberate
  display choice, not something the spike's scores dictate* — with the explicit note that no
  threshold can structurally separate confidently-wrong from confidently-right for this model.
  That comment is the right thing to have written; it stops a future reader from mistaking these
  constants for validated science.
- Single-result edge case (`margin = top.score`) is handled and tested.

### Nits (non-blocking)

1. **`food.js:96-98` is now a stale comment.** It reads: *"AI photo analysis is the one route that
   costs us money per call, so it's the only thing gated by the trial/subscription."* After this
   ticket, photo analysis costs nothing per call, and `/analyze-text` is *also* gated by
   `requireActiveAccess`. Both halves of the sentence are now wrong. Mild irony: this ticket
   diligently fixed the two *other* stale comments the plan named (`index.js`'s startup warning,
   `api.ts`'s `caveat` doc) and walked straight past this one, which sits nine lines above the
   route it modified.
2. **A failed pre-warm poisons the singleton permanently.** `classifierPromise` caches the rejected
   promise, so if the boot-time model load fails (no network on first run, corrupt cache, disk
   full), every `/food/analyze` 502s until the process restarts — there is no reset or retry. The
   code comment in `index.js:62` states this outcome plainly, so it is disclosed rather than
   hidden, and it correctly does *not* cause an unhandled rejection (the boot handler attaches a
   `.catch`, and the route's `try/catch` handles later awaits). Acceptable for now; worth a retry
   path when the backend is actually hosted.
3. **Two identically-styled banners can stack.** `log.tsx:472-481` renders the low-confidence banner
   and the `caveat` banner with the *same* `styles.lowConfidence` treatment. Before this ticket
   that was rare; now **every** photo scan carries a caveat, and the anchor-near-top and
   couldn't-identify paths carry `confidence: 'low'` *as well* — so the common failure case shows
   two visually identical warning blocks in a row. This is not a bug, and it is exactly the
   question plan Step 4 item 4 asked Step 6 to answer with eyes on the rendered page. See §6.
4. **`mimetype` is client-declared, not sniffed.** `food.js:110` validates
   `req.file.mimetype` against a 3-entry allowlist, but multer takes that from the multipart part
   header — an authenticated client can declare `image/jpeg` and send arbitrary bytes, which then
   reach libvips. Pre-existing pattern (the Claude path had the same validation) but newly
   *consequential*, because the bytes are now decoded in-process. See §9.

None of these four is merge-blocking.

## 4. Honesty / discipline

**Verdict: meets the 006-009 norm, and on the mitigated-not-solved framing it exceeds it.**

I checked each of the four specific items asked of me:

**(a) Mitigated-not-solved framing for CLIP's failure mode — clear, and not overclaimed anywhere.**
I went looking for overclaiming and did not find it. The outcome doc puts it in bold in the
*"Verdict up front"* section, before any list of accomplishments: *"This does NOT mean CLIP's core
failure mode is solved... still exists at the model layer, exactly as the spike found it, and is
mitigated — not eliminated."* Residual risk #1 then does something better than restating it: it
distinguishes the case the code **does** catch (dog photo — anchor at position 2, caught by
`anchorNearTop`) from the case it **does not** (cat photo — top-2 was "pancakes," another food
label, so no anchor appears in the top 3 at all and a wrong food wins outright). That is a precise,
self-critical account of the mitigation's actual boundary rather than a generic disclaimer. I
verified it against the spike's own tables: the cat row reads top-1 waffles 0.415, top-2 pancakes
0.289 — no anchor in sight. The doc's characterization is accurate.

I also checked the *code* comments for overclaiming, since that's where optimism usually leaks:
`local-food-analysis.js:8-14` states the thresholds "only decide what banner the confirm screen
shows, never whether a result is returned," and explicitly cites the spike's finding that no
threshold can separate confidently-wrong from confidently-right. Consistent with the doc.

**(b) The deliberate override of the spike's own "don't proceed" recommendation — recorded, twice.**
In the plan (Design summary: *"This plan overrides that recommendation on product grounds... This
override is deliberate and is recorded here explicitly, not silently"*) and again as residual risk
#2 in the outcome doc, which names all three alternatives the spike wanted tried first (anchor
prompt engineering, a larger CLIP variant, a two-stage binary gate) and states plainly that **none
of them were implemented**. I read the spike's Recommendation section myself: it does indeed say
"Do not proceed straight to an implementation plan," and it does name exactly those three. The
override is faithfully characterized, and the justification (the confirm screen changes the cost of
a wrong guess from silent data corruption to one edit) is legitimate and is something the spike
genuinely did not have visibility into. Nothing here reads as though the spike endorsed this path.

**(c) The unlisted-food residual risk — named, with the right emphasis.** Residual risk #3 states
that a food absent from the 36-label list will always score against the *closest* label, cites the
spike's real "grilled chicken breast → roasted vegetables at 56.6%" case as an instance of exactly
that failure, and — critically — states that *"the confirm screen only helps if the user actually
notices the suggested name/macros are wrong."* That last clause is the honest part. It resists the
tempting conclusion that a confirm screen makes model errors harmless, and correctly frames it as
"a real, standing risk of the whole design, not a closed gap."

**(d) The nutrition-data caveat — clear, and in three places.** Stated in "What was built" item 2,
repeated as residual risk #5, and — the part I care most about — **written into the generator
script's own header** with a `do not remove` marker, so a future maintainer editing that file
encounters it. I read the script header: it explains *why* no live pull happened (no FDC API key
configured) **and** the independent reason a live pull wouldn't have been sufficient anyway (FDC
entries are branded/generic ingredients, not composed dish servings, so "one taco" needs a human
judgment call regardless). That second reason is the more useful one and it is not something a doc
written to look good would have bothered to include. The generated file carries the same note.

I spot-checked the data for credibility against well-known USDA values: banana 105 kcal, apple 95,
bagel 289, oatmeal 166/cup, white rice 205/cup, 2 large scrambled eggs 182. These are correct to
the level claimed. All 36 rows have finite, non-negative macros and a non-empty
`servingDescription` (verified programmatically). The claim "manually-set estimates cross-checked
against typical USDA values" is an accurate description of what is in the file — neither inflated
into "USDA-sourced" nor falsely deprecated.

## 5. Risk assessment — actual blast radius

**Verdict: bounded, and the safety net is real. I verified it by reading, not by trusting.**

### The confirm-before-log gate

`grep -rn "createLog" app/src` (excluding tests) returns exactly **two** call sites in the entire
app:

- `log.tsx:270` — inside `confirmSave()`, which is reachable **only** from the "Save to today"
  `PressableScale` in the `step === 'review'` card (`log.tsx:525`). Its first two statements are
  `if (!result) return;` and the blank-`foodName` guard.
- `log.tsx:291` — inside `logFromStash()`, which logs a previously-saved frequent food on an
  explicit user tap. Not an AI path at all; `source: 'manual'`; no model output involved.

On the backend, `grep "INSERT INTO food_logs"` returns exactly **one** site: `food.js:227`, inside
`POST /food/logs`. And `POST /food/analyze` (`food.js:108-128`) performs **zero** writes — its
entire body is validate → call → `res.json(result)` → catch/502. So:

**There is no path by which a model suggestion reaches `food_logs` without the user tapping Save on
a screen that shows the suggested name and all four macros in editable fields.** `bumpStreak()` and
wardrobe-unlock derivation hang off `POST /food/logs` only, so an unconfirmed suggestion also has no
gamification side effects. The `Discard` action (`log.tsx:520`) calls `reset()`, which clears both
`result` and `rawResultRef` without any network call.

### So what is the realistic blast radius of a misclassification?

**A wrong prefill the user must actively accept.** Concretely, the worst realistic outcome: a user
photographs a food not on the 36-label list (or a non-food whose anchor didn't place top-3), the
review screen prefills a wrong name and a wrong standard-serving macro set, the user does not read
it, taps Save, and their daily calorie total is wrong by up to a few hundred calories for one
entry. That is a **data-quality** harm in a personal calorie tracker — self-correcting on the next
day's log, editable/deletable after the fact, with no effect on any other user, no financial
exposure (the AI is now free per call), and no security or privacy consequence.

Three factors bound it further:

1. **Every photo scan now carries a caveat.** The non-anchor success path always sets the
   "database default, not measured from your photo" caveat, so the review screen always tells the
   user the macros are a reference serving. The user is never shown a bare, confident-looking
   number.
2. **The degrade path is a usable screen, not an error.** "Couldn't identify" returns HTTP 200 with
   an empty name, zeroed macros, and an explicit caveat — plus the new client guard that blocks Save
   with *"Enter a food name before saving."* rather than a raw API 400. The user's next action is
   always available.
3. **The failure is visible, not silent.** This is the qualitative difference from attempt 2's
   rejection. A closed softmax returning `grilled_salmon` at 99.1% for a chicken breast produced a
   confident wrong answer with nothing to look at; here the wrong answer arrives pre-labeled as a
   suggestion needing review.

**The honest counterweight**, which the outcome doc states and I agree with: this only works if the
user reads the screen. Habituation is the real long-term risk — and nit #3 (§2) makes it concrete,
since the common failure case now stacks two identically-styled warning banners, which is precisely
the shape of UI that trains people to tap past warnings.

### Availability / operational risk

Higher than the data risk, and mostly deferred by the fact that the backend isn't hosted:

- **Cold start.** Pre-warm `await`s **before** `app.listen()`, so on a fresh deploy with an empty
  cache the port does not open until a 605MB download plus a ~36.5s model load completes. A
  container orchestrator with a default health-check grace period would kill and restart the
  process in a loop, never reaching a healthy state. The trade-off itself is sound and deliberately
  reasoned (the client has no `AbortController`, so a lazy first load would hang a real user's UI) —
  but it needs a readiness-probe/grace-period configuration at deploy time.
- **Memory.** The spike measured 881MB peak RSS; my own run showed 722MB after a single
  classification. A 512MB-class instance will OOM. Sizing decision for whoever hosts this.
- **Per-scan CPU.** ~1.1-2.0s inference, single-threaded and CPU-bound, in-process with the Express
  event loop. Concurrent scans will queue and degrade. Fine at current scale; a real constraint
  later.
- **Poisoned singleton** on pre-warm failure (nit #2).

|---|---|---|---|
| Model/library integration wrong (input shape, template, cache dir) | **Highest** — this is where the two real bugs actually were | **Yes** | I ran the real 605MB model end-to-end and got a well-formed result with the correct cache dir |

The two uncovered rows are the honest residue. The critical point for the merge decision is that
**this ticket does not change the review screen's rendering.** I read the full `log.tsx` diff: +31
lines, entirely additive — one `useRef`, one early-return guard, three ref assignments, two ref
clears. **Not one line of the review card's JSX (`log.tsx:470-535`) was touched.** So there is no
rendering change here that a live browser session could regress-catch. The screen that would be
inspected is the same screen that shipped in 009 and was live-verified then.

What *is* new to the rendered page is the **content** flowing into unchanged JSX: every photo scan
now carries a caveat, and low confidence is now common rather than rare. That makes the residual
question a **UX-quality** question — "does this banner still read as signal?" — not a correctness
question. And I can now state that question far more precisely than "we didn't look," because
reading the JSX surfaced the specific thing to look at (nit #3): when `confidence === 'low'` **and**
a caveat is set — now the standard failure presentation — the card renders **two banners with the
identical `styles.lowConfidence` treatment, stacked**. Whether that reads as emphasis or as noise is
exactly what Step 6(c) and plan Step 4 item 4 were meant to determine, and it cannot be determined
from code.

### Why that does not justify blocking

1. **A UX-legibility judgment is not a merge gate.** If the double banner reads badly, the fix is a
   styling change to one component — a small follow-up ticket, not a rework of this one. Nothing
   about merging makes that fix harder.
2. **Blocking has a real cost and buys little.** The gap would be closed by an interactive session
   that neither the implementer, the tech-lead, nor I can convene. Holding an otherwise-complete,
   twice-tech-lead-approved, zero-QA-bug change indefinitely on a subjective UX check — one that a
   screenshot read by an agent answers only weakly — is not a good trade.
3. **Precedent exists.** Ticket 009 merged with several disclosed deploy-time carryovers. This
   project's established norm is that verification-environment gaps are carried explicitly, not
   used to block, provided they are named. They are named here, in unusual detail.
4. **The severity ceiling is low.** Per §5, the worst outcome behind this specific gap is a user
   habituating to a warning banner and accepting a wrong prefill — bounded, self-correcting,
   single-user, non-financial.
5. **The evidence substituted is genuinely stronger than a browser click on the axes that matter.**
   A Playwright session would not have caught the `hypothesis_template` double-wrapping bug (the

- The **double-banner question is written down** as the concrete thing to inspect, so whoever runs

## 9. New finding: supply-chain advisories introduced by this ticket

Not raised in any prior review round. Recorded here because it is the most consequential thing I
found, and because the outcome doc should carry it.

`npm audit --omit=dev` in `backend/`:

```
4 high severity vulnerabilities, 0 critical/moderate/low

sharp <0.35.0                              high   fixAvailable: false
  └ inherited libvips vulnerabilities: CVE-2026-33327, CVE-2026-33328,
    CVE-2026-35590, CVE-2026-35591  (GHSA-f88m-g3jw-g9cj)
onnxruntime-node 1.22.0-dev… - 1.29.0-dev… high   fixAvailable: false
adm-zip <0.6.0                             high   fixAvailable: false
  └ crafted ZIP file triggers 4GB memory allocation  (GHSA-xcpc-8h2w-3j85)
@huggingface/transformers *                high   (depends on the above)
```

**Why there is no clean fix.** `@huggingface/transformers@4.2.0` **is the latest published version**
and it pins `sharp: ^0.34.5`. The patched `sharp@0.35.3` exists but is outside that range, so npm
cannot resolve it — hence `fixAvailable: false`. Remediation requires an upstream transformers
release, or a semver-violating `overrides` pin that would need its own testing.

**Reachability, honestly assessed:**

- **`sharp`/libvips: reachable with attacker-controlled bytes.** The path is
  `POST /food/analyze` → multer memory buffer → `new Blob([buffer])` → `RawImage.fromBlob` →
  `sharp` → libvips decode. `food.js:110` validates only the **client-declared** mimetype (multer
  reads it from the multipart header), so an authenticated client can declare `image/jpeg` and post
  up to 8MB of arbitrary bytes into an image decoder with known CVEs. Note this is a **new** class
  of surface: the Claude path base64-encoded the bytes and shipped them off-host — nothing decoded
  untrusted images in this process before this ticket.
- **`adm-zip`: low reachability.** It arrives via `onnxruntime-node` and is used to unpack native
  binaries from a vendor archive at install time — not per-request with user input.

**Why this still isn't a merge blocker:**

1. **Nothing in this ticket's code can fix it.** No upstream fix exists. Blocking the merge changes
   nothing about the exposure.
2. **The backend isn't hosted anywhere** (no Dockerfile / fly.toml / render.yaml — pre-existing gap,
   explicitly out of scope). There is no internet-reachable instance to attack today.
3. **The endpoint requires authentication *and* an active trial/subscription.**
   `foodRouter.use(requireAuth)` (`food.js:94`) then `requireActiveAccess` (`:108`) — I confirmed a
   live unauthenticated request returns `401`. An attacker needs a valid Clerk account in good
   billing standing. That is not an anonymous surface, and it is attributable.
4. **The 8MB multer cap** bounds the memory-amplification class of attack somewhat.

So: **merge, but this is carryover #1 and a hard gate before anything is hosted.** It also belongs
in the outcome doc — a reader deciding whether to deploy this should not have to re-derive it.

## Merge rationale

Four review rounds have already been spent on this ticket, and the sequence tells a good story: the
plan's first draft was rejected for inventing a screen that already existed; the second was approved
with six specific fixes, all applied; the implementation's first round was rejected for a
`.gitignore` pattern that would have broken the entire backend on a fresh clone; the second was
approved after that fix was verified in both directions. QA found zero bugs across two rounds. That
is the pipeline working as designed, and the artifact it produced holds up under independent
inspection.

What I most wanted to be true, and independently confirmed:

- **The invariant that mattered most is structural.** `foodName` cannot be a raw model string,
  because there is exactly one path to it and that path is a primary-key lookup into checked-in
  data with a single writer. Seven mutations confirm the suite defends it; the design confirms it
  wouldn't have needed to.
- **The integration is genuinely wired,** not just plausibly coded. I ran the real 605MB model
  through the relocated cache and got the same result the outcome doc reported, booted the real
  server, and got a 200 on `/health` and a 401 on unauthenticated `/analyze`.
- **Every reported number is real.** 121/121, 327/327, and all seven coverage figures reproduced
  exactly. The 3.37s backend suite runtime independently proves the lazy dynamic import is doing its
  job.
- **The honesty bar is met and then exceeded.** The mitigated-not-solved framing leads the document
  rather than trailing it; the mitigation's exact boundary is characterized correctly (dog caught,
  cat not); the spike's own "don't proceed" recommendation is recorded as a deliberate override in
  two places; the unlisted-food risk names the uncomfortable dependency on the user actually
  noticing; the nutrition-data caveat appears three times including in the generator's own header;
  and an inert `allowScripts` block the build itself added is retracted in writing rather than
  quietly deleted.

The gaps are real and I am not minimizing them. Step 6 never happened, `ai_raw_response` has no test,
mobile is untested, and the dependency chain carries four unfixable-today advisories. But none of
them is a defect in the shipped code, all are now named with specific closure criteria, and the
worst realistic user-facing outcome of this change remains: *a wrong food name, pre-filled, on a
screen that says "please review before saving," which the user must actively accept.* That is a
materially better failure mode than what shipped before it (a photo scan that was broken outright)
and than what was rejected twice before it (a confident wrong answer with nothing to review).

**MERGE.** Commit on the user's explicit request, per this project's standing convention.
